## 1단계: 평가 세트와 기준값

평가 질문 80개(`eval/questions.jsonl`)를 만들고 지금 서비스 검색의 정확도를 쟀다.

| 항목 | 내용 |
|---|---|
| 질문 수 | 80개 (Pt.2 11, Pt.3 50, Pt.5 19) |
| 작성 | 생성 76개, README 예시 4개 |
| 정답 | 질문마다 정답 조항(ref, clause)을 지정, 각각 chunk 1개에 대응 |
| 지표 | R@k (상위 k개 안에 정답이 있는 비율), MRR@10 (정답 순위 역수의 평균) |
| 스크립트 | `eval/evaluate.py` |
| 결과 | `eval/results/baseline.md` |

서비스는 상위 6개 발췌문을 LLM에 넘기므로 **하이브리드 R@6**이 실제 서비스 정확도에 해당한다.

| 검색 방식 | R@1 | R@3 | R@6 | R@10 | MRR@10 |
|---|---|---|---|---|---|
| 벡터 | 0.613 | 0.787 | 0.850 | 0.887 | 0.708 |
| 키워드 (BM25) | 0.637 | 0.825 | 0.863 | 0.900 | 0.736 |
| 하이브리드 (서비스) | 0.625 | 0.825 | 0.912 | 0.963 | 0.736 |

주의: 평가 질문 대부분을 규정 조항을 보면서 썼으므로 규정 문구와 단어가 겹치는 쪽으로 치우쳤을 수 있다. 최종 수치를 내기 전에 사람이 조항을 보지 않고 쓴 질문을 20개 이상 더하는 것이 좋다.

## 2단계: 검색 임베딩 모델 학습

### 학습 데이터

| 항목 | 내용 |
|---|---|
| 방법 | chunk마다 Gemini(gemini-3.5-flash-lite)에게 설계자 질문 3개를 쓰게 함 (도면 변경, 설계 질문, 현장 말투) |
| 스크립트 | `train/make_dataset.py` |
| 결과 파일 | `train/data/queries.jsonl` (1.4MB) |
| 처리한 chunk | 4,704개 (전체 4,781개 중 평가 정답 chunk 77개 제외) |
| 질문이 생긴 chunk | 4,057개 (Pt.2 866, Pt.3 858, Pt.5 2,333) |
| 질문 없는 chunk | 647개 (적용 범위, 참고 규격 목록, 용어 정의 등 요구사항이 없는 조항) |
| 학습 쌍 | 12,169개 |

### 학습

| 항목 | 값 |
|---|---|
| 기반 모델 | BAAI/bge-small-en-v1.5 (지금 서비스 모델) |
| 손실 함수 | MultipleNegativesRankingLoss (배치 안의 다른 chunk를 오답으로 사용) |
| 설정 | 1 에폭, 배치 32, 학습률 2e-5, 학습 시 최대 256토큰, 아래 6개 층 고정 |
| 시간 | CPU 103분 (381 step) |
| loss | 0.96에서 0.16으로 감소 |
| 스크립트 | `train/finetune.py` |
| 모델 | `models/bge-small-dnv/` (133MB, GitHub 용량 제한 때문에 ignore 처리, 로컬에만 있음) |

### 평가 결과

| 검색 방식 | 지표 | 기존 | 학습 모델 |
|---|---|---|---|
| 하이브리드 | R@1 | 0.625 | 0.650 |
| 하이브리드 | R@6 | 0.912 | 0.912 |
| 하이브리드 | R@10 | 0.963 | 0.950 |
| 하이브리드 | MRR@10 | 0.736 | 0.752 |
| 벡터 | R@1 | 0.613 | 0.588 |
| 벡터 | MRR@10 | 0.708 | 0.706 |

- 질문별로는 하이브리드 기준 순위가 오른 질문 14개, 내려간 질문 9개, 같은 질문 57개였다.
- 질문 80개에서 1문항은 1.25%포인트라 이 정도 차이는 우연과 구분할 수 없다.
- 결론: 의미 있는 개선이 없어 **서비스에는 적용하지 않았다**.
- 결과 파일: `eval/results/finetuned.md`

### 원인 확인

평가 질문과 학습 질문(Gemini 생성)의 말투 차이 때문인지 확인했다. 학습에서 뺀 chunk 68개에 대해 학습 데이터와 같은 방식으로 질문 204개를 만들어 비교했다(`eval/synthetic_check.py`, 결과 `eval/results/synthetic_check.md`).

| 검색 방식 | 지표 | 기존 | 학습 모델 |
|---|---|---|---|
| 벡터 | R@1 | 0.735 | 0.770 |
| 벡터 | R@6 | 0.961 | 0.936 |
| 하이브리드 | R@1 | 0.819 | 0.814 |
| 하이브리드 | R@6 | 0.980 | 0.971 |

같은 종류의 질문에서도 거의 좋아지지 않았으므로 말투 차이가 원인은 아니다. 추정한 원인은 다음과 같다(검증하지 않은 추측).

| 추정 원인 | 근거 |
|---|---|
| 생성 질문이 너무 쉬움 | 기존 모델도 R@6 0.96~0.98 |
| 오답이 무작위라 쉬움 | 실제로 틀리는 것은 옆 조항, 다른 Part의 비슷한 조항인데 이를 따로 가르치지 않음 |
| 학습 폭이 좁음 | CPU 시간 때문에 1 에폭, 아래 6개 층 고정 |

## 3단계: 공식 계산 엔진

규정 PDF의 공식은 이미지라 텍스트 추출이 안 된다. PDF 원문 페이지를 보고 공식과 표 값을 손으로 옮겼다. 숫자 계산은 LLM이 하지 않고 파이썬 코드가 한다.

| 공식 | 근거 조항 | 결과 |
|---|---|---|
| 재료계수 k | Pt.3 Ch.3 Sec.1 [2.2] Table 2 | k |
| 최소 판 두께 | Pt.3 Ch.6 Sec.3 [1.1.1] Table 1 | t (mm, net) |
| 횡압력을 받는 판 두께 | Pt.3 Ch.6 Sec.4 [1.1.1] Table 1 | t (mm, net) |
| 보강재 단면계수 | Pt.3 Ch.6 Sec.5 [1.1.2] Table 3~5 | Z (cm3, net) |
| 선체 최소 단면계수 | Pt.3 Ch.5 Sec.2 [1.3] | Z (m3, gross) |
| 선체 최소 관성모멘트 | Pt.3 Ch.5 Sec.2 [1.5.2] | I (m4, gross) |

- 보조 정의: Cw는 Ch.4 Sec.4, fr은 Ch.4 Sec.3, L2와 단위는 Ch.1 Sec.4에서 옮겼다.
- 결과는 단계별로 "기호, 식, 숫자 대입, 값, 단위, 근거 조항"을 남긴다. 5단계에서 이것을 표로 보여 준다.
- 적용 범위를 벗어난 입력은 오류로 막는다. 예: R_eH가 460 초과, 관성모멘트 계산에서 L이 90 m 이하.
- 코드가 다루지 않는 각주와 조건은 결과에 메모로 붙인다. 예: 부식 여유 미포함, 모든 하중 조건 중 최댓값 필요.
- 테스트: 손계산 기대값으로 만든 24개 모두 통과했다(`python -m unittest discover tests`). 다만 테스트는 코드가 옮긴 식대로 계산하는지만 확인한다. PDF에서 식을 옳게 옮겼는지는 눈으로 대조해야 하며, 출처 쪽 번호는 `formulas/hull.py` 머리 주석에 적었다.
- 웹 서버에는 아직 연결하지 않았다. Dockerfile도 수정해야 한다.

| 파일 | 내용 |
|---|---|
| `formulas/core.py` | 입력·계산 단계·결과 구조, 표 출력 |
| `formulas/hull.py` | 공식 6개와 규정 표 값 |
| `formulas/__init__.py` | `calculate()`, `describe()` |
| `formulas/__main__.py` | `python -m formulas demo` 예제 출력 |
| `tests/test_formulas.py` | 단위 테스트 24개 |
